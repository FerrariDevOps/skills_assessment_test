# Scenario 1: KMS key rotation

## 1. What are the main challenges in applying key rotation? And what impacts can you identify?

The first challenge concerns keys whose material comes from the on-premises HSM, and keys like this do not support automatic rotation.
For a long time the only way out was to create a new key and switch the alias. The good news is that since 06/06/2025 AWS has launched [on-demand rotation for keys with imported key material](https://aws.amazon.com/about-aws/whats-new/2025/06/aws-kms-on-demand-key-rotation-imported-keys) as shown in the [usage guide on the Security Blog](https://aws.amazon.com/blogs/security/how-to-use-on-demand-rotation-for-aws-kms-imported-keys/). The real restriction, according to the [`RotateKeyOnDemand` documentation](https://docs.aws.amazon.com/kms/latest/developerguide/rotating-keys-on-demand.html), is being a symmetric encryption key, you only need to invoke the rotation from the primary key, and it applies to the whole set. This covers practically all the keys presented. So the real challenge is not "how to rotate", it is "building the process", generating new material in the HSM, wrapping it with the KMS wrapping key and importing it, dozens of times, once per key, with the current granularity, one key per service per environment.

This brings me to the second point, where some confusion tends to arise, rotation happens on the key, not on S3, RDS or DynamoDB. KMS swaps the material it uses to encrypt new data, but keeps the old material only to decrypt what already exists, AWS itself describes this, in almost these terms "when you use the rotated key to decrypt, KMS uses the material that was used to encrypt that data.....because KMS transparently decrypts with the right material, you can use a rotated key in AWS applications and services without changing code" [How key rotation works](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html#rotate-keys-how-it-works). So the operational impact of on-demand rotation is, in practice, zero, the ARN and the alias of the key do not change, services keep pointing to the same place and do not even notice it rotated. This is also written in the documentation, "the KMS key is the same logical resource, regardless of how many times its material changes, the properties of the key do not change". The [page dealing with the particularities of imported material](https://docs.aws.amazon.com/kms/latest/developerguide/importing-keys-considerations.html) reinforces this specifically for our BYOK case, "the current material is used both to encrypt and decrypt, but the other materials (non current) can only be used to decrypt".

Asymmetric and HMAC keys do not qualify for on-demand rotation, but this does not really amount to a real challenge for this project. S3, RDS and DynamoDB, the three services in the diagram, only accept a symmetric encryption key to encrypt data at rest. So every `dev-s3`, `dev-rds`, `dev-ddb` key is already born symmetric. The full key replacement path remains relevant for a different reason, if a key is compromised, the correct response is also to replace the key, not just rotate the material, and then the same re-encryption path applies. It is for that scenario that the impacts below really matter.

- In **S3** changing the key only affects new objects, the ones that already exist stay on the old key until someone runs a bulk re-encryption such as S3 Batch Operations, for example.
- In **RDS** you cannot change the key of an existing instance. The path is snapshot, copy encrypting with the new key, and restore, which means a cutover window.
- In **DynamoDB** it is straightforward, the key change is online.

Since the material is not generated by KMS, AWS does not guarantee its durability the way it does for native material, so losing the copy in the HSM means losing the key for good and AWS does not give the material back. And if the keys were imported with an expiration date, that also needs to enter the rotation calendar, because when it expires KMS deletes the material on its own and the key stops working. This is a point that can be handled quite simply with monitoring, KMS publishes the `SecondsUntilKeyMaterialExpires` metric on CloudWatch for every key with imported material that has an expiration configured, and AWS itself documents how to set up an alarm, for example, warning when less than 30 days remain, that triggers an SNS topic before the key becomes unusable. [Create a CloudWatch alarm for expiration of imported key material](https://docs.aws.amazon.com/kms/latest/developerguide/imported-key-material-expiration-alarm.html).

Another challenge is that KMS only allows **25 on-demand rotations per key, for the whole life of the key**. AWS itself documents this both in the guide and in the API reference, *"You can perform on-demand key rotation a maximum of 25 times per KMS key"* [Perform on-demand key rotation](https://docs.aws.amazon.com/kms/latest/developerguide/rotating-keys-on-demand.html) and [RotateKeyOnDemand](https://docs.aws.amazon.com/kms/latest/APIReference/API_RotateKeyOnDemand.html). With annual rotation that gives 25 years of headroom per key, so it is not a capacity problem, the reason I take this seriously is that any retry automation needs to know this ceiling and never burn through that quota by retrying endlessly.

## 2. From your perspective, what are the steps for applying key rotation (high level description)?

It starts with an RFC, a short document explaining what is going to change, why, who approves it and what the rollback plan is, reviewed by security, compliance and architecture. It defines the rollout in stages, Dev, with an observation period, then Int and only then Prod, each one a new gate, never all at once, the rollback, since KMS has no "undo the rotation" API, the new material stays in `PENDING_ROTATION` state until promotion and can be discarded with no impact at all (`DeleteImportedKeyMaterial`) if something is wrong before `RotateKeyOnDemand` [Import new key material](https://docs.aws.amazon.com/kms/latest/developerguide/importing-keys-import-key-material.html#import-new-key-material), after promotion there is no more automatic undo, only forward fix, generate the correct material and rotate again.

The RFC is treated as code, a Markdown file in the infrastructure repository itself, going up as a pull request with `CODEOWNERS` pointing to security, compliance and architecture as required reviewers, the merge is already the recorded approval, with the whole history saved in git. It is the de facto community pattern for this kind of decision, versioned RFC plus pull request review, along the same lines that HashiCorp documents for the GitOps flow applied to Terraform [GitOps workflow](https://developer.hashicorp.com/well-architected-framework/define-and-automate-processes/process-automation/gitops).

The technical execution uses **deployment approvals on protected environments** in GitLab, Dev, Int and Prod marked as protected environments, each with its own required approvers, and the execution job blocked until the approval happens, all recorded in GitLab itself [Deployment approvals](https://docs.gitlab.com/ci/environments/deployment_approvals/).

GitLab, as per scenario 3, runs on an EC2 instance inside AWS, there is a single GitLab server, and it is the one that coordinates the pipeline. The GitLab Runner is a separate component from the server, the agent that actually executes the jobs, and the documentation itself recommends installing it on a different machine from the one hosting GitLab, and it can be spread across different networks and infrastructures, as long as it can reach the server to fetch work [GitLab Runner](https://docs.gitlab.com/runner/). That is why the pipeline crosses two networks without needing a second GitLab anywhere, a self-hosted GitLab Runner inside the datacentre, with direct access to the HSM cluster, and another GitLab Runner running as an EC2 instance in the AWS account itself, both registering and fetching jobs from the same GitLab server. The HSM side only exists to reach the cluster, it reaches the GitLab server through a private link between the datacentre and the VPC with a Direct Connect and does not receive any AWS credentials, because it never calls the KMS API directly. The AWS side of the pipeline is responsible for the steps that talk to KMS.

Data passing between the two sides uses GitLab CI's native **artifacts** mechanism, passing a file from one stage to the other between jobs, including between jobs on different runners [Job artifacts](https://docs.gitlab.com/ci/jobs/job_artifacts/). This works because nothing that travels between the two sides is a plaintext secret, the wrapping public key and the import token are not sensitive, and the material that leaves the HSM cluster already comes out encrypted, generating and packaging in a single operation, without the plaintext leaving the hardware boundary, is a standard HSM capability, documented both by the Thales/Luna integration guide specifically for BYOK with AWS KMS and by AWS CloudHSM's own `wrapKey` utility [Luna HSM Integration Guide: AWS Key Management Services](https://cpl.thalesgroup.com/sites/default/files/content/integration_guides/field_document/2020-07/007-013808-001_AWS_KeyManagementServices_SafeNetLunaHSM_IntegrationGuide_RevC.pdf) and [Export an AWS CloudHSM key using KMU](https://docs.aws.amazon.com/cloudhsm/latest/userguide/key_mgmt_util-wrapKey.html).

Authentication on the AWS side uses **OIDC from GitLab CI/CD**, instead of a fixed role on the runner's EC2 instance, because I imagine this runner is shared across several pipelines and several teams, an instance role would apply to any job running on it, not just the rotation one. The OIDC token carries claims such as `project_path`, `namespace_id`, `environment` and `ref`, and the IAM role's trust policy uses these claims to only let that specific job, from that specific project, assume that specific role [Configure OpenID Connect in AWS](https://docs.gitlab.com/ci/cloud_services/aws), [Setting up OpenID Connect with GitLab CI/CD to provide secure access to environments in AWS accounts (AWS Partner Network Blog)](https://aws.amazon.com/blogs/apn/setting-up-openid-connect-with-gitlab-ci-cd-to-provide-secure-access-to-environments-in-aws-accounts/).

**1. Generate the new material inside the on-premises HSM.** This happens on the HSM cluster, inside the datacentre. Authentication on this job is not a single credential, production HSMs normally require partition credentials plus client certificate authentication, and material generation stays under **dual control**, meaning two custodians must authorise the operation, each one knowing only part of the credential for accessing the HSM. This is a formal requirement from the PCI SSC itself, the **PCI PIN Security Requirements** determines that unencrypted key material must be loaded into HSMs using the principles of **dual control and split knowledge**, with all hardware and key loading passwords also under dual control [PCI PIN Security Requirements, v2.0](https://listings.pcisecuritystandards.org/documents/PCI_PIN_Security_Requirements_v2.pdf). KMS requires a 256 bit symmetric key (AES 256) as material for symmetric encryption keys [Requirements for imported key material](https://docs.aws.amazon.com/kms/latest/developerguide/importing-keys-conceptual.html#importing-keys-material-requirements), so that is what the HSM cluster generates. And the most important point, the "generate and package" operation happens as a single thing inside the HSM boundary (`wrap-on-export`), so the plaintext material is never written to disk nor does it travel over the network at any point, only the already encrypted blob leaves as an artifact for the next stage.

**2. Ask KMS for the public wrapping key and the import token ([`GetParametersForImport`](https://docs.aws.amazon.com/kms/latest/developerguide/importing-keys-get-public-key-and-token.html)).** This happens on the AWS side of the pipeline, authenticated by OIDC with the job scoped role described above. The pair, public key plus token, is not sensitive, so this job publishes both as an artifact, which the next job, on the HSM cluster, downloads automatically, which is standard GitLab CI behaviour between stages.

**3. Encrypt the new material with that wrapping key.** This happens back on the HSM cluster, together with step 1 (`wrap-on-export`), using the `RSA_AES_KEY_WRAP_SHA_256` algorithm, a hybrid scheme in which the material is encrypted with an AES key generated on the spot, and that AES key is encrypted with the RSA wrapping public key that came from step 2, the result leaves the HSM already protected, ready to become an artifact.

**4. Import as new material (`ImportKeyMaterial` with `NEW_KEY_MATERIAL`).** Back on the AWS side of the pipeline, which takes the artifact with the encrypted blob produced in step 3 and the import token from step 2 and calls `ImportKeyMaterial`. The material is only kept as a pipeline artifact, for the minimum time between one stage and the other, never on disk otherwise, the artifact expiration is set to a few hours, well below the token's 24 hour validity, without storing that blob in any bucket or queue beyond GitLab's own mechanism. Proof that this happened is already recorded on its own, since every `ImportKeyMaterial` call creates a CloudTrail entry.

**5. Trigger the rotation (`RotateKeyOnDemand`).** Still on the AWS side of the pipeline, before this step, the script calls `ListKeyRotations` to confirm that the new material really is in `PENDING_ROTATION`. Only after that does it call `RotateKeyOnDemand`, which promotes the material to current and keeps the old one only to decrypt.

**Permissions.** The role that the AWS side of the pipeline assumes via OIDC, one role per environment, Dev, Int, Prod, only has `kms:GetParametersForImport`, `kms:ImportKeyMaterial`, `kms:RotateKeyOnDemand` and `kms:ListKeyRotations`, restricted to the ARN of the keys in that environment through `Resource` in the IAM policy, and since KMS always validates through the key policy as well, these same actions need to be granted to that principal directly in the key policy of each key. The HSM cluster receives no AWS permission at all, it never calls the KMS API, it only exchanges artifacts through the pipeline itself. The calls, `get_parameters_for_import`, `import_key_material`, `list_key_rotations`, `rotate_key_on_demand`, run in a Python script with boto3, directly in the AWS runner's job in the pipeline.

The script validates the state of each key with `list_key_rotations` before moving on to the next step, this is the "check before proceeding" pattern, since KMS has eventual consistency and changes can take a moment to propagate, it records a structured log of each step which is useful both for debugging and as evidence for the regulator, at the end, it updates the status of the corresponding RFC.

**Triggering the pipeline.** The job that calls the KMS API is tied to a protected environment, Dev, Int or Prod, with mandatory deployment approval, the pipeline can be started manually or on a schedule, but that particular job stays held, waiting for approval, until the approvers defined for that environment approve within GitLab itself, once approved, it runs automatically, with no further manual triggering needed.

**Failure handling.** It depends on where the pipeline stops. If it fails between steps 2 and 4 that means it has not imported yet, because nothing changed on the key, the restart happens from step 2 onward, since the expired token forces a new pair to be generated anyway. If it fails after step 4 but before step 5, the material already imported, but still `PENDING_ROTATION`, there is also no production issue, the key keeps operating on the current material, and step 5 can be run again later, or, if that material should no longer be used, it can be deleted with no impact (`DeleteImportedKeyMaterial`). If `RotateKeyOnDemand` itself fails, the API can return a `ConflictException` if an automatic rotation is already in progress or about to start in the next few minutes, in that case the script does not keep insisting without stopping, it logs the failure and stops, because KMS only allows **25 on-demand rotations per key** for the whole life of the key as mentioned earlier, and no automation should burn through that quota with automatic retries. Any failure after a certain number of attempts becomes an alert, CloudWatch Alarm to SNS, for the team responsible for the RFC to decide the next step, instead of the automation insisting on its own.

For dozens of keys, the pipeline reads a versioned inventory file in the same repository as the RFC, for example, `keys/prod.yaml`, listing the alias or ARN of each key in scope, and iterates over that list, one rotation at a time, recording the result of each one individually, instead of rotating dozens of keys as a single monolithic operation that either passes entirely or fails entirely. Adding or removing a key from the scope is a change to that file, reviewed through the same pull request flow as the RFC, not a decision made at runtime.

Lastly, the complete evidence is recorded on its own, the RFC approved in git, the approval recorded on GitLab's protected environment and CloudTrail, which already records `ImportKeyMaterial` and `RotateKeyOnDemand`, together they form the trail shown to the regulator. The final step is turning on continuous monitoring, which is the next question.

## 3. How can we monitor, with a managed AWS service, the resources (RDS, DynamoDB, S3) that are not compliant with rotation?

Before getting to the tool, one detail that changes the way of thinking about the problem, as I explained in question 1, rotation is not a property of the resource, it is a property of the key. AWS itself confirms this in the definition of the managed rotation rule, its **Resource Type is `AWS::KMS::Key`**, not `AWS::S3::Bucket`, `AWS::RDS::DBInstance` or `AWS::DynamoDB::Table` [cmk-backing-key-rotation-enabled](https://docs.aws.amazon.com/config/latest/developerguide/cmk-backing-key-rotation-enabled.html), the APIs that check rotation state (`GetKeyRotationStatus`, `ListKeyRotations`) also only take a `KeyId`, never a bucket, an instance or a table. So "non compliant resource" in practice means "resource that uses a key whose material is out of date". Monitoring needs to follow that path, resource to key to rotation state.

The right service for this is **AWS Config**, which supports `AWS::KMS::Key` as a monitored resource type [Supported resource types](https://docs.aws.amazon.com/config/latest/developerguide/resource-config-reference.html) and exists exactly to continuously evaluate whether resources comply with a rule, aggregating that view across several accounts in one place.

The managed rule that already exists, [`cmk-backing-key-rotation-enabled`](https://docs.aws.amazon.com/config/latest/developerguide/cmk-backing-key-rotation-enabled.html), does not work on its own here, since it checks the automatic rotation flag, and AWS's own documentation warns that this flag "is not supported for asymmetric KMS keys, HMAC KMS keys, KMS keys with imported key material, or KMS keys in custom key stores", which is exactly the case of our BYOK keys. Writing a custom rule backed by Lambda is the path documented by AWS for this kind of extension, described in the official guide [Creating AWS Config custom Lambda rules](https://docs.aws.amazon.com/config/latest/developerguide/evaluate-config_develop-rules_lambda-functions.html), and the AWS Security Blog itself uses this same pattern to extend KMS checks beyond the managed rules, in [How to use AWS Config to determine compliance of AWS KMS key policies to your specifications](https://aws.amazon.com/blogs/security/how-to-use-aws-config-to-determine-compliance-of-aws-kms-key-policies-to-your-specifications/). So the custom rule, for each S3 bucket, RDS instance and DynamoDB table.

1. finds out which KMS key is associated;
2. checks that key's rotation history, `ListKeyRotations`, which shows the materials and when each one became current;
3. flags the resource as non compliant if the last rotation is past the deadline set in the policy, for example, one year, or if the resource is still on an old key, in the case of manual rotations.

Then, to have the view across all accounts together, I use a **Config Aggregator** in one account, for example Security, and roll the rule out to the whole organisation with a conformance pack. If needed, Security Hub can be used and an automatic alert set up, EventBridge to SNS, when something becomes non compliant.

## 4. What is the best way to protect the key material during its transport from the HSM to AWS KMS?

The answer here is roughly "follow KMS's own manual", AWS documents that this is exactly the design goal of the import process. In the words of the documentation itself, *"Your key material never leaves the HSM in plain text. It is decrypted only while it is in use and only within AWS KMS HSMs."* [Protecting imported key material](https://docs.aws.amazon.com/kms/latest/developerguide/import-keys-protect.html).

So we should first get the public wrapping key from KMS and an import token via `GetParametersForImport`, which are only valid for 24 hours. With that public key, we can encrypt the material **inside the HSM itself**, without it ever leaving in plain text. The algorithm used is `RSA_AES_KEY_WRAP_SHA_256`, in the official table of wrapping algorithms, AWS lists the options "in preference order" and this is the first on the list, as well as being the only one required when the material being imported is an RSA private key [Select a wrapping algorithm](https://docs.aws.amazon.com/kms/latest/developerguide/importing-keys-get-public-key-and-token.html#select-wrapping-algorithm). This encrypts the material with an AES key generated on the spot, and encrypts that AES key with KMS's RSA public key. Only after that is the encrypted material and the import token sent to `ImportKeyMaterial`.

The part that really guarantees security here is not the TLS on the API call, which also exists, it is just one more layer, but rather the fact that the private key that decrypts that package never leaves AWS's own HSMs, and it is worth separating the two HSMs involved clearly, because they are different systems, our on-premises HSM only holds the AES 256 material we are importing, the RSA wrapping key pair, the public key we download and the private one that decrypts it on the other side, is generated and lives entirely inside the HSM infrastructure that underpins the AWS KMS service itself, a separate system, operated by AWS and validated under the [FIPS 140-3 Cryptographic Module Validation Program](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/4884), which not even AWS itself has direct access to in order to extract a key in plain text. So even if someone intercepted the traffic, there would be no way to decrypt the material without access to that internal KMS infrastructure, which is out of our reach and out of reach of any external attacker. That is why the right answer is not "use a VPN" or anything like that, it is to follow this key wrapping flow that the service itself requires.
