# Scenario 4: Backup policy with AWS Backup (Terraform module)

The full implementation is in the [`terraform-aws-backup/`](terraform-aws-backup/) directory, with a usage README and a working example in `examples/complete`, and the module passes `terraform validate`. Here I explain how it meets each requirement of the design.

The design has three vaults in three different places, so the module takes three provider aliases, `aws.source` for the Prod account in Frankfurt, `aws.dr` for the Prod account in Ireland, and `aws.central` for the Backup account in Frankfurt. Each provider creates its own vault with its own KMS key, with automatic rotation switched on, and its own Vault Lock configuration via [aws_backup_vault_lock_configuration](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/backup_vault_lock_configuration).

The backup plan lives in the source account and has one rule with frequency and retention coming from variables, with a daily cron by default, and two `copy_action` blocks inside that same rule, one pointing at the Ireland vault, which is the cross region copy, and another at the Backup account vault, which is the cross account copy, each copy with its own retention, exactly as the design asks, all natively supported by [aws_backup_plan](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/backup_plan).

Resource selection carries the most important catch in the module. The requirement is `ToBackup=true` together with `Owner=<owner>`, both tags at the same time, and in `aws_backup_selection` that forces the use of the `condition` block, because conditions are combined with AND, whereas the `selection_tag` block, which looks like the obvious choice, combines with OR and would select any resource carrying just one of the two tags, that distinction is documented in [Assigning resources](https://docs.aws.amazon.com/aws-backup/latest/devguide/assigning-resources.html). The selection uses `resources = ["*"]` to cover every supported type, with the tags coming in through a variable and evaluated as `aws:ResourceTag`.

Vault Lock on all three vaults runs in compliance mode, with `changeable_for_days` set the lock becomes immutable after the grace period, not even the account root can remove it, and that is what meets the requirement of preventing malicious and accidental deletion, documented in [AWS Backup Vault Lock](https://docs.aws.amazon.com/aws-backup/latest/devguide/vault-lock.html). This has a side effect I flagged in the README, a vault with recovery points inside resists a `terraform destroy`, the AWS API refuses the deletion with the error Backup vault cannot be deleted because it contains recovery points, the destroy fails and the resources stay in the Terraform state, managed and intact, nothing is left half deleted, and with the lock in compliance mode not even `force_destroy` on [aws_backup_vault](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/backup_vault) gets past that within the retention window, because deleting the recovery points themselves is exactly what the lock denies. That is exactly the intention of the design, but it needs to be agreed with whoever is testing it.

And since the resources end up living in state, the state itself deserves the same security care as the rest of the design. HashiCorp is explicit about this, Terraform state and plan files contain detailed information about your infrastructure, including resource attributes and metadata that can contain sensitive values, and the guidance is to treat state as sensitive data, that is in [Manage sensitive data in Terraform](https://developer.hashicorp.com/terraform/language/manage-sensitive-data#background). For this challenge I would keep the state in an [S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3) with `encrypt` plus `kms_key_id`, which encrypts both the state and the lock files with SSE-KMS, and with S3's native locking via `use_lockfile`, which is the current standard, the documentation itself says DynamoDB based locking is deprecated and will be removed. On the bucket, a policy that denies everything except two conditions, requests coming through the S3 VPC endpoint, and here is an adjustment to the idea, the right mechanism is not an IP range, it is the `aws:SourceVpce` condition with the endpoint ID, which is exactly the pattern documented in [Controlling access from VPC endpoints with bucket policies](https://docs.aws.amazon.com/AmazonS3/latest/userguide/example-bucket-policies-vpc-endpoint.html), and requests whose principal is the pipeline's OIDC role, via `aws:PrincipalArn`. Since the GitLab Runner on the AWS side runs on an EC2 instance inside the VPC, it reaches the bucket through the gateway endpoint without ever going out to the internet, and no access from outside the VPC or outside that role works. There is just one thing the page itself warns about, that policy also blocks console access, so it is worth leaving an administrative break glass role on the exceptions list to avoid locking the key inside the car.

The cross account copy has prerequisites that do not show up on the diagram. Both accounts need to be in the same AWS Organizations organisation, the destination vault needs a vault policy allowing `backup:CopyIntoBackupVault` for the source account, which the module already creates, and the vaults need a customer managed key, an AWS managed key does not work for cross account, and for resource types without full AWS Backup management the source key still needs to be shared with the destination account, all of that is in [Creating backup copies across AWS accounts](https://docs.aws.amazon.com/aws-backup/latest/devguide/create-cross-account-backup.html).

The service role that AWS Backup assumes uses the official managed policies, `AWSBackupServiceRolePolicyForBackup` and `AWSBackupServiceRolePolicyForRestores`, plus the S3 variants, since tag based selection can reach buckets too.

A note on the current landscape I would raise when reviewing this design, AWS now has [logically air-gapped vaults](https://docs.aws.amazon.com/aws-backup/latest/devguide/logicallyairgappedvault.html), generally available [since August 2024](https://aws.amazon.com/about-aws/whats-new/2024/08/general-availability-aws-backup-logically-air-gapped-vault/), a type of vault that already comes with Vault Lock in compliance mode built in, encrypted by default with an AWS owned key, and that can be shared with other accounts via AWS RAM to speed up restore during an incident. For the part of the requirement that is an isolated, immutable copy in another account, it solves it with fewer moving parts than a standard vault plus lock plus vault policy. I implemented the module faithful to the design that the security, compliance and architecture teams already validated, but I would note this alternative for a future iteration.

General references, [AWS Backup Developer Guide](https://docs.aws.amazon.com/aws-backup/latest/devguide/whatisbackup.html), [aws_backup_plan](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/backup_plan), and [aws_backup_vault_lock_configuration](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/backup_vault_lock_configuration) on the Terraform Registry.
